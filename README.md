# Resilience Toolkit

## Подготовка

У данного задания есть базовая и бонусная версии.

### hw_base

Для **основного задания** название ветки должно быть `hw_base`

> git checkout -b **hw_base**

### hw_bonus

Для **бонусного задания** название ветки должно быть `hw_bonus`

> git checkout -b **hw_bonus**

В бонусной версии нужно реализовать ещё четыре компонента и сделать всё решение потокобезопасным.
Бонусные тесты запускаются вместе с базовыми, поэтому сначала доведите до конца `hw_base`.

## Задание

Любой сервис рано или поздно начинает ломаться: внешний API отвечает ошибками, база тормозит,
клиент присылает в сто раз больше запросов, чем вы можете обработать. Чтобы одна поломка не положила
всё остальное, вызовы «опасных» операций оборачивают в **политики отказоустойчивости**.

В этом задании вам предстоит написать небольшую библиотеку из таких политик в пакете
[`internal/resilience`](./internal/resilience). Все политики реализуют один интерфейс и вкладываются друг в друга:

```go
type Policy interface {
	Do(op func() error) error
}
```

Например, так выглядит защита вызова внешнего сервиса: не больше десяти запросов в секунду, а если сервис
лёг, не долбить его и подождать:

```go
limiter, err := resilience.NewTokenBucket(clock, 10, 100*time.Millisecond)
if err != nil {
	return err
}
breaker, err := resilience.NewCircuitBreaker(clock, resilience.Config{
	FailureThreshold:  5,
	OpenTimeout:       30 * time.Second,
	HalfOpenSuccesses: 2,
})
if err != nil {
	return err
}
policy, err := resilience.Chain(limiter, breaker)
if err != nil {
	return err
}

err = policy.Do(func() error {
	return callExternalService()
})
```

### Структура пакета

```
Clock ◄───────────────────────── внедряется во все политики
  ├─ RealClock                   настоящее время
  └─ FakeClock                   «ручное» время для тестов

Policy ── Do(op func() error) error
  ├─ TokenBucket                 ограничивает частоту вызовов      (base)
  ├─ CircuitBreaker              перестаёт звать сломавшийся сервис (base)
  ├─ Chain(policies...)          склеивает политики в одну          (base)
  ├─ Retry ──► Backoff           повторяет упавшие вызовы с паузами (bonus)
  │              ├─ ConstantBackoff
  │              ├─ ExponentialBackoff
  │              └─ FullJitter / EqualJitter  (случайность, bonus)
  └─ Bulkhead                    ограничивает число одновременных вызовов (bonus)

Limiter[K] ──► map[K]*TokenBucket   отдельный лимит на каждого пользователя (bonus)
```

Файлы, которые **уже готовы и не должны изменяться**: `clock.go`, `errors.go`, `policy.go`
(в `errors.go` есть и все ошибки, которые вам нужно возвращать, и маленький помощник `failIf`, см. ниже).
Остальные файлы содержат заготовки с `panic("not implemented")`, которые нужно заменить своим кодом.
Добавлять в структуры любые поля и вспомогательные типы можно, менять сигнатуры экспортируемых
функций и методов нельзя.

### Ограничения

Разрешены импорты `errors`, `fmt`, `iter`, `math`, `sync` и `time` (`sync` нужен только в бонусной версии,
а из `time` разрешены типы и константы, но не `time.Now` и `time.Sleep`, см. ниже).
Пакеты `sort`, `slices`, `container/*` и сторонние библиотеки запрещены.

**Ни одна политика не имеет права вызывать `time.Now()` или `time.Sleep()` напрямую.**
Время берётся только из `Clock`, который передаётся в конструктор. Именно поэтому тесты не ждут реальных
секунд и работают мгновенно: они подставляют `FakeClock`, у которого `Sleep` не блокирует, а просто
переводит время вперёд, а `Advance(d)` двигает его вручную.

### Ошибки конструкторов

Паниковать из-за неверных аргументов нельзя: конструкторы возвращают `(значение, error)`. При ошибке значение
должно быть нулевым (`nil` для указателей).

Конструктор проверяет **все** аргументы и сообщает **обо всех** найденных проблемах сразу. Каждая проблема имеет
свою ошибку из `errors.go` (`ErrNilClock`, `ErrInvalidCapacity`, `ErrInvalidInterval`, ...), и они не
пересекаются: `errors.Is` для ошибки возвращает `true` ровно для тех из них, которые относятся к вашим
неверным аргументам, и `false` для остальных. Если неверных аргументов несколько, возвращается одна ошибка,
в которой есть все соответствующие (её удобно собрать через `errors.Join`; помощник `failIf` из `errors.go` даёт
`nil`, если условие не выполнено, а `errors.Join` пропускает `nil`):

```go
return nil, errors.Join(
	failIf(clock == nil, ErrNilClock),
	failIf(capacity <= 0, ErrInvalidCapacity),
	failIf(interval <= 0, ErrInvalidInterval),
)
```

Тексты ошибок не проверяются, проверяется только `errors.Is`. Паниковать можно (и нужно) лишь там, где это
прямо указано в контракте: паника внутри `op` пробрасывается наружу, а не гасится.

Подсказка: аргументы `NewTokenBucket` и `NewLimiter` проверяются одинаково, поэтому проверку удобно вынести
в одну общую функцию. Не надо создавать «пробное» ведро только ради проверки аргументов.

## Контракт (hw_base)

### 1. TokenBucket — ограничитель частоты

```go
func NewTokenBucket(clock Clock, capacity int, interval time.Duration) (*TokenBucket, error)
func (b *TokenBucket) Allow() bool
func (b *TokenBucket) Tokens() int
func (b *TokenBucket) Do(op func() error) error
```

«Ведро» вмещает не больше `capacity` токенов. Каждый вызов операции стоит один токен. Новый токен появляется
раз в `interval`, пока ведро не заполнено. Ведро **изначально полное**, то есть первые `capacity` запросов
проходят подряд (burst), а потом не чаще одного запроса за `interval`.

- `Allow` забирает токен и возвращает `true`, если токен был. Иначе возвращает `false` и ничего не меняет.
- `Tokens` возвращает, сколько токенов доступно прямо сейчас. **Токены не забирает.**
- `Do` забирает токен и вызывает `op`, возвращая её ошибку как есть (токен при этом тратится в любом случае).
  Если токена нет, возвращает `ErrRateLimited`, а `op` **не вызывается**.
- Токены не обновляются в фоне. Сколько их накопилось, считается по `Clock` при обращении.
- Дробный остаток времени не должен теряться: при `interval = 1s` и пустом ведре через 2.5 секунды в нём
  2 токена, а ещё через 0.5 секунды их 3.
- Пока ведро полное, время «не копится»: если ведро простояло полным 9 секунд из 10, а потом из него взяли
  токен, то новый токен появится через полный `interval` после этого, а не через 1 секунду.
- Количество токенов никогда не превышает `capacity`, даже после очень долгого простоя (подумайте
  о переполнении целых чисел при больших промежутках).
- `Allow` не должен делать аллокаций.
- `NewTokenBucket` возвращает `ErrNilClock`, если `clock == nil`, `ErrInvalidCapacity`, если `capacity <= 0`,
  и `ErrInvalidInterval`, если `interval <= 0` (все подходящие сразу, см. «Ошибки конструкторов»).

### 2. CircuitBreaker — «предохранитель»

```go
type State int // Closed, Open, HalfOpen; у State есть метод String()

type Config struct {
	FailureThreshold  int
	OpenTimeout       time.Duration
	HalfOpenSuccesses int
	IsFailure         func(error) bool
}

func NewCircuitBreaker(clock Clock, cfg Config) (*CircuitBreaker, error)
func (c *CircuitBreaker) State() State
func (c *CircuitBreaker) Do(op func() error) error
```

Если сервис упал, бессмысленно продолжать слать ему запросы: он только хуже себя чувствует, а вы тратите
время на заведомо провальные ожидания. Предохранитель в этом случае временно перестаёт вызывать операцию
и отвечает ошибкой сразу.

Состояния и переходы:

```
          FailureThreshold ошибок подряд
 ┌────────┐ ───────────────────────────────► ┌──────┐
 │ Closed │                                  │ Open │ ◄─────────────┐
 └────────┘ ◄──────────────┐                 └──────┘               │
                           │                    │ прошло           ошибка
          HalfOpenSuccesses│                    │ OpenTimeout      при пробе
          успешных проб    │                    ▼                   │
                           │               ┌──────────┐             │
                           └────────────── │ HalfOpen │ ────────────┘
                                           └──────────┘
```

- **Closed.** Операции выполняются. Ошибки считаются **подряд идущими**: любой успех обнуляет счётчик.
  Когда подряд накопилось `FailureThreshold` ошибок, предохранитель переходит в `Open`.
- **Open.** `op` **не вызывается**, `Do` возвращает `ErrCircuitOpen`. Когда с момента перехода в `Open`
  прошло `OpenTimeout` (граница включительно, то есть ровно `OpenTimeout`
  уже достаточно), предохранитель считается `HalfOpen`.
- **HalfOpen.** Пропускаются пробные вызовы. После `HalfOpenSuccesses` успешных подряд предохранитель
  возвращается в `Closed`. Первая же ошибка отправляет его обратно в `Open`, и таймер `OpenTimeout`
  отсчитывается заново от момента этой ошибки. При каждом переходе все счётчики (ошибок и успешных проб)
  обнуляются.

Дополнительные правила:

- `State()` возвращает **актуальное** состояние: если `Open` уже отстоял `OpenTimeout`, то вернуть нужно
  `HalfOpen`, даже если после этого не было ни одного вызова `Do`.
- `Do` возвращает ошибку `op` как есть (то же самое значение, без обёрток).
- `IsFailure` определяет, считать ли ошибку отказом. Если `nil`, отказом считается любая ошибка `!= nil`.
  Ошибка, которая отказом не считается, всё равно возвращается вызывающему, но для предохранителя
  это такой же успех, как и `nil`.
- Если `op` паникует, то это считается отказом, а паника **пробрасывается дальше** без изменений.
  То же верно, если паникует сама `IsFailure`: вызов считается отказом, паника пробрасывается, а предохранитель
  остаётся рабочим (в том числе освобождается слот пробы в `HalfOpen`).
- `State()` только читает: просмотр состояния никогда не меняет предохранитель.
- `String()` у `State` возвращает `"closed"`, `"open"`, `"half-open"`, а для любого другого значения
  `"State(7)"` (с самим числом).
- `NewCircuitBreaker` возвращает `ErrNilClock`, если `clock == nil`, а также `ErrInvalidFailureThreshold`,
  `ErrInvalidOpenTimeout` и `ErrInvalidHalfOpenSuccesses`, если соответствующее поле `Config` не положительно.

### 3. Chain — композиция политик

```go
func Chain(policies ...Policy) (Policy, error)
```

`Chain(a, b, c).Do(op)` должно работать так же, как `a.Do(func() error { return b.Do(func() error { return c.Do(op) }) })`,
то есть первая политика самая внешняя, последняя ближе всего к операции.

- `Chain()` без аргументов просто вызывает `op`.
- Любая политика в цепочке вправе не вызывать `next` (например, `TokenBucket` отказал), тогда `op` не вызывается,
  а `Do` возвращает ошибку этой политики.
- Результат `Chain` можно использовать повторно и вкладывать в другие `Chain`.
- Если среди политик есть `nil`, `Chain` возвращает `nil` и `ErrNilPolicy` (сразу, а не при первом `Do`).
- Последующие изменения переданного среза не должны влиять на уже созданную цепочку.

Порядок политик важен: `Chain(bucket, breaker)` не считает отказы лимитера ошибками сервиса, а
`Chain(breaker, bucket)` считает (и может «открыть» предохранитель только потому, что вы шлёте слишком
много запросов).

## Контракт (hw_bonus)

### 4. Backoff и Retry — повтор упавших вызовов

```go
type Backoff interface {
	Delay(attempt int) time.Duration // attempt нумеруется с 1
}

type ConstantBackoff struct{ D time.Duration }

type ExponentialBackoff struct { /* ваши неэкспортируемые поля */ }

func NewExponentialBackoff(base, max time.Duration, factor int) (ExponentialBackoff, error)

type RetryConfig struct {
	MaxAttempts int
	Backoff     Backoff
	Retryable   func(error) bool
}

func NewRetry(clock Clock, cfg RetryConfig) (*Retry, error)
func (r *Retry) Do(op func() error) error

type RetryError struct {
	Attempts int
	Last     error
}
```

**Backoff.**

- `ConstantBackoff.Delay` всегда возвращает `D`.
- `ExponentialBackoff` создаётся через `NewExponentialBackoff(base, max, factor)`, поля у типа неэкспортируемые.
  `Delay(attempt)` возвращает `base * factor^(attempt-1)`, но не больше `max`.
  Например, `base = 100ms, factor = 2, max = 1s` даёт `100ms, 200ms, 400ms, 800ms, 1s, 1s, ...`.
- `max == 0` означает «без ограничения». В этом случае при переполнении результат **не уходит в минус**,
  а остаётся равным `math.MaxInt64` наносекунд.
- Результат корректен для любого `attempt`, вплоть до `math.MaxInt`, и вычисляется быстро (подумайте,
  что произойдёт при `factor = 1` и миллиарде попыток).
- `attempt < 1` считается первой попыткой (паники нет).
- Нулевое значение `ExponentialBackoff{}` безопасно: `Delay` у него всегда возвращает `0`.
- `NewExponentialBackoff` возвращает `ErrInvalidBase`, если `base <= 0`, `ErrInvalidFactor`, если `factor < 1`,
  и `ErrInvalidMax`, если `max < 0` или `0 < max < base`. Значения `max == base`, `max == 0` и `factor == 1` допустимы.

**Retry.** `MaxAttempts` — общее число вызовов `op`, включая первый (минимум 1).

- Если `op` вернула `nil`, `Do` возвращает `nil`.
- Если ошибка не подлежит повтору (`Retryable != nil` и вернула `false`), она возвращается **немедленно
  и без обёрток**. `Retryable == nil` означает «повторять любую ошибку».
- Между попытками вызывается `clock.Sleep(Backoff.Delay(n))`, где `n` — номер только что провалившейся
  попытки (с 1). `Sleep` вызывается только если задержка **строго положительна**, и **никогда после
  последней попытки**. `Backoff == nil` означает «без пауз».
- Когда все `MaxAttempts` попыток провалились, возвращается `*RetryError{Attempts, Last}`, где `Last` —
  ошибка **последней** попытки.
- `(*RetryError).Error()` возвращает строку `"retries exhausted after 3 attempts: boom"` (для `Attempts = 3`
  и `Last` с текстом `boom`).
- `(*RetryError).Unwrap() []error` устроен так, что одновременно работают
  `errors.Is(err, ErrRetriesExhausted)` и `errors.Is(err, <ошибка последней попытки>)`.
- Паника в `op` не перехватывается.
- `NewRetry` возвращает `ErrNilClock`, если `clock == nil`, и `ErrInvalidMaxAttempts`, если `MaxAttempts < 1`.

`Retry` хорошо сочетается с `CircuitBreaker`: пока предохранитель открыт, повторы получают `ErrCircuitOpen`,
паузы между ними продвигают часы, и в какой-то момент проходит пробный вызов.

> Повторы кажутся безобидными, но именно они чаще всего добивают упавший сервис, если все клиенты повторяют
> одновременно. В следующем разделе способ этого избежать, и в бонусных тестах есть небольшая симуляция,
> которая измеряет его эффект на «сервисе», а не проверяет отдельные функции.

### 5. Jitter — не приходить всем одновременно

```go
type Rand interface {
	Float64() float64 // число из [0, 1)
}

func NewFullJitter(inner Backoff, rnd Rand) (*FullJitter, error)
func NewEqualJitter(inner Backoff, rnd Rand) (*EqualJitter, error)
```

Если тысяча клиентов споткнулась в одну и ту же секунду и у всех одинаковый `ExponentialBackoff`, то они
повторят запрос **тоже все вместе**, через 100 мс, потом через 200, и так далее: сервис получает пики
(«гром стада»), хотя в среднем нагрузка небольшая. Лечится случайностью в паузе. Оба типа реализуют `Backoff`
и оборачивают другой `Backoff`:

- `FullJitter.Delay(attempt)` берёт задержку `d` внутреннего `Backoff` для той же попытки и возвращает случайное
  значение, равномерно распределённое в `[0, d)`.
- `EqualJitter.Delay(attempt)` оставляет половину задержки и рандомизирует вторую: результат в `[d/2, d)`
  (то есть `d/2` плюс случайная часть оставшейся половины; для нечётного `d` достижим весь диапазон, включая `d-1`).
- Если внутренняя задержка `<= 0`, результат `0`, и `Rand` **не вызывается**. Иначе `rnd.Float64()` вызывается
  **ровно один раз** на каждый вызов `Delay`.
- Результат всегда лежит в нужном диапазоне, даже если `Rand` нарушил контракт и вернул `1`, число больше `1`
  или отрицательное (такие числа обрезаются). Никаких переполнений даже при `d = math.MaxInt64`.
- `FullJitter` и `EqualJitter` можно использовать из нескольких горутин, даже если переданный `Rand` сам не
  потокобезопасен (например, `*rand.Rand`): обращения к `Rand` нужно сериализовать.
- Источник случайности приходит снаружи (в тестах это `*rand.Rand` из `math/rand/v2` с фиксированным seed или
  заготовленная последовательность), поэтому тесты детерминированы. Глобальный `math/rand` использовать нельзя.
- Конструкторы возвращают `ErrNilBackoff`, если `inner == nil`, и `ErrNilRand`, если `rnd == nil` (обе сразу,
  если нужно).

### 6. Limiter — отдельный лимит на ключ

```go
func NewLimiter[K comparable](clock Clock, capacity int, interval time.Duration) (*Limiter[K], error)
func (l *Limiter[K]) Allow(key K) bool
func (l *Limiter[K]) Do(key K, op func() error) error
func (l *Limiter[K]) Tokens(key K) int
func (l *Limiter[K]) Size() int
func (l *Limiter[K]) Sweep() int
func (l *Limiter[K]) Idle() iter.Seq[K]
```

Для каждого ключа (пользователь, IP-адрес, ...) заводится свой `TokenBucket` с одними и теми же параметрами.
Ведро создаётся при первом `Allow`/`Do` для ключа (сразу полным).

- `Allow` и `Do` ведут себя как у `TokenBucket`, но с отдельным ведром на ключ.
- `Tokens(key)` для неизвестного ключа возвращает `capacity` и **ничего не создаёт**.
- `Size()` — число ключей, у которых сейчас есть ведро.
- Если ключей миллионы, память не должна расти вечно. Ведро, которое **полностью заполнено**, неотличимо
  от нового (оно ведёт себя ровно так же, как если бы его не было), поэтому его можно безопасно удалить.
  `Sweep()` удаляет все такие вёдра и возвращает, сколько их было. Поведение `Allow`, `Do` и `Tokens`
  от вызова `Sweep` меняться **не должно**, а у остальных ключей токены не должны пропадать.
- `Idle()` возвращает итератор по ключам, ведра которых сейчас полные (то есть по тем, которые удалил бы `Sweep`),
  в произвольном порядке, ничего не удаляя. Итератор должен корректно обрабатывать `break`. В теле цикла
  `for k := range l.Idle()` разрешено вызывать любые методы того же `Limiter`, поэтому блокировку на
  время вызова `yield` держать нельзя.
- `Allow` для уже существующего ключа не делает аллокаций.
- `NewLimiter` возвращает те же ошибки в тех же случаях, что и `NewTokenBucket`.

### 7. Bulkhead — «переборка»

```go
func NewBulkhead(limit int) (*Bulkhead, error)
func (b *Bulkhead) Do(op func() error) error
func (b *Bulkhead) InFlight() int
```

`TokenBucket` ограничивает число запросов **в единицу времени**, но не защищает от медленных вызовов: при лимите
«10 в секунду» и вызовах по 30 секунд через минуту в работе окажется 600 операций. `Bulkhead` ограничивает число
операций, которые выполняются **одновременно**. Название взято из кораблестроения: перегородки в корпусе не дают
пробоине в одном отсеке затопить весь корабль.

- `Do` занимает один из `limit` слотов и вызывает `op`, возвращая её ошибку как есть. Если свободных слотов нет,
  возвращается `ErrBulkheadFull`, а `op` **не вызывается** (и не ждёт освобождения места).
- Слот освобождается, когда `op` завершилась: и после успеха, и после ошибки, и **после паники** (паника при этом
  пробрасывается дальше без изменений).
- `InFlight()` возвращает, сколько операций выполняется прямо сейчас. Отклонённые вызовы в это число не входят.
- Время для `Bulkhead` не нужно, поэтому `Clock` в конструктор не передаётся.
- `Do` не делает аллокаций.
- `NewBulkhead` возвращает `ErrInvalidLimit`, если `limit <= 0`.
- `Bulkhead` потокобезопасен (см. следующий раздел), иначе у него нет смысла.

### 8. Потокобезопасность

В бонусной версии `TokenBucket`, `CircuitBreaker`, `Bulkhead`, `Limiter`, `FullJitter` и `EqualJitter` можно использовать из нескольких горутин
одновременно (тесты запускаются с `-race`). Помимо отсутствия гонок:

- `TokenBucket` и `Limiter` не выдают в сумме больше токенов, чем положено, и не теряют их даже при
  параллельных `Sweep`.
- `op` в `CircuitBreaker.Do` выполняется **без удержания блокировки**: операция вправе обращаться
  к тому же предохранителю (например, вызвать `State()`), и это не должно приводить к deadlock.
- В состоянии `HalfOpen` одновременно выполняется **не больше одной** пробной операции.
  Все остальные вызовы в это время получают `ErrCircuitOpen`.
- Результат операции, которая началась в одном состоянии предохранителя, а завершилась уже
  в другом (предохранитель успел открыться, подождать и закрыться), игнорируется и не влияет на новое состояние.

## Скрипты
Для запуска скриптов на курсе необходимо установить [go-task](https://taskfile.dev/docs/installation)

`go install github.com/go-task/task/v3/cmd/task@latest`

Перед выполнением задания не забудьте выполнить:

```bash
task update
```

Запустить линтер:
```bash
task lint
```

Запустить базовые тесты:
```bash
task test-base
```

Запустить бонусные тесты:
```bash
task test-bonus
```

Бонусные тесты включают проверки `Retry`, `Backoff`, `Jitter`, `Bulkhead`, `Limiter`, потокобезопасности и небольшую симуляцию («гром стада»). Перед ними также
запустите базовые тесты. Проверить решение на гонки можно командой `task test-race` (нужен компилятор C,
то есть `gcc`, например, внутри WSL).

Обновить файлы задания
```bash
task update
```

Принудительно обновить файлы задания
```bash
task force-update
```

Скрипты работают на Windows, однако при разработке на этой операционной системе
рекомендуется использовать [WSL](https://learn.microsoft.com/en-us/windows/wsl/install)
